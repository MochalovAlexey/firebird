# Гилёв в обычном клиенте 1С на Firebird

13 ноября 2026 года **полный функциональный прогон завершён** настоящим толстым
клиентом `1cv8 8.5.4.1306` через отдельный кластер 1С и Release-сборку Firebird.
Форма «Тест Гилёва : 2.1.1.48» показала **100%**, **«TPC: Тест завершен!»** и
результат **2,14**. Подготовленная база находится в
`/home/aleksey/dev/1c/firebird-gilev/data/gilev_32k.fdb`.

Кнопка запуска нажата в 13:35:09 MSK; итоговый экран сохранён в 14:15:28.
Это около 40 минут от запуска, включая очистку; отдельное чистое время
benchmark здесь не измерялось. Стенд и окно с результатом оставлены работающими.

[Команды запуска и добавление существующей базы в GUI](GILEV_GUI.md).
Сервер 1С: `127.0.0.1:12541`, имя базы: `GilevFirebird`. PgWire слушает 25432,
native Firebird — 23050. Приватный `connection.json` содержит настройки и
учётные данные стенда; скрипт запуска не выводит пароль.

## Изменения для запуска

- `970ad45d54`: постоянный стенд, отдельный кластер и launcher обычного клиента.
- `0b67064650`: исправление native semijoin с пустым списком conjuncts;
  дефект воспроизведён без PG DELETE USING на предыдущем engine.
- `329c6d184b`: PG4 DELETE USING для фактической очистки Гилёва, с преобразованием
  в native DELETE/EXISTS. [Поддержанный SQL-профиль](DELETE_USING.md).

Первый Debug-запуск остановился на неподдержанном DELETE USING; очистка
откатилась. Второй прошёл очистку и записывал документы без новых SQL-ошибок,
но был остановлен штатно для перехода на Release. Перед остановкой короткая
native-проверка увидела 1631 документ. Эта попытка не считается завершённым
тестом. Debug runtime сохранён в `runtime-debug`; текущий `runtime` содержит
Release. Настройки надёжности записи не изменялись.

## Граница приёмки

Проверяется работа на перенесённой базе, а не создание новой базы средствами
1С или полная совместимость PostgreSQL. Сохраняются 16 неперенесённых expression
indexes, три sequence defaults и остальные ограничения [BACKLOG](../BACKLOG.md).
Конфликт двух редакторов и обновление версий реальных объектов отдельно не приняты.

Это один полный функциональный прогон с подробной trace. Его балл не является
сопоставимым измерением производительности. Read-only срез
Release обнаружил 98 медленных COMMIT за 32,7 с, медиана 126 мс и обычно 57
записей страниц; точная причина задержки не установлена. Debug дополнительно
показал многочисленные внутренние prepare; их вклад отдельно не измерен. Оптимизации
metadata cache и ослабление надёжности записи ради результата не применялись.
Устойчивость повторных полных прогонов и конкурентного редактирования остаётся
отдельной проверкой; успешный запуск не закрывает весь roadmap.

Исходный PostgreSQL и его данные не изменялись. Изменения сохраняются только
локальными коммитами, без push.
