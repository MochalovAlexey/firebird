# Путь до запуска 1С и теста Гилёва

Срез на 11 ноября 2026 года: ревизия `5bbdaa763d`, APP-10 прошёл review и независимую приёмку.
APP-11 реализован поверх неё, целевые проверки прошли; изменения оставлены на review без commit.
Этот файл показывает готовность прикладного сценария; конкретные незавершённые
работы и ограничения ведутся в [BACKLOG](../BACKLOG.md), доказательства — в
[VALIDATION](../VALIDATION.md). Обновлять после следующих прикладных этапов.

**Основной wire/SQL-фундамент работает. Реальное открытие базы 1С на Firebird
и тест Гилёва пока не приняты. Существенная часть прикладной совместимости ещё
впереди.** Процент готовности по числу выполненных маленьких этапов или SQL
был бы недостоверным: один SET и многопользовательская нагрузка несопоставимы.

## Подтверждённые возможности

| Участок | Что подтверждено | Граница доказательства |
|---|---|---|
| Сетевое подключение | Реальный PostgreSQL wire через libpq/psql, параллельно native endpoint; выполнение на Firebird | Linux/Super и локальный TCP; это ещё не приёмка реального клиента 1С |
| Начало сессии | Identity-запрос, фиксированные SET, все семь startup SET | Три настройки намеренно без эффекта; версия/Startup фактического клиента 1С ещё требуют проверки |
| SQL/исполнение | Simple scripts с остановкой на ошибке; Extended/prepared/portals; typed последовательные `$n`, native postfix casts, literal LIMIT | Общая PG-грамматика и произвольные PG types не реализованы |
| Транзакции | BEGIN, COMMIT/ROLLBACK, I/T/E, savepoints/recovery, native visibility | Не полная эквивалентность isolation/locks PostgreSQL; advisory locks ещё нет |
| Binary data | Native BLOB output как bytea; text/binary input через OCTETS и native MOVE | Вход ≤65533 bytes на значение; выход ограничен общим DataRow budget. Это не SQL bytea type/index semantics |
| Native namespace identity | APP-10 принят: устанавливаемый PGWIRE_COMPAT registry, стабильные IDs, native/libpq, права/concurrency/restart | Native DDL под user savepoint запрещён; PG names/types/visibility и selected04 ещё не реализованы |
| Публичные namespace IDs | APP-11 на review: PG_CATALOG.PG_NAMESPACE над APP-10, atomic installer, точные имена/IDs, read-only, text/binary/native/libpq и transaction visibility PASS | BIGINT/VARCHAR, wire20/1043, uppercase labels; нет PG oid/name/regnamespace, nspowner/nspacl, pg_class/visibility/temp namespace |
| Прикладные формы | Чтение конфигурации selected06 и запись selected23 неизменённым SQL; форма 92 parameters, включая 68 BLOB | Синтетические таблицы/данные; реальная схема, конфигурация и исходный Bind 1С не приняты |

## Где находимся относительно конечной цели

| Контрольная точка | Состояние |
|---|---|
| Обычный libpq-клиент исполняет совместимый SQL в Firebird | Достигнута в описанном профиле |
| Необходимый базовый обмен параметрами и binary payload | Достигнут ограниченный, проверенный профиль |
| Каталоги и SQL, необходимые для проверки/открытия базы 1С | Не готовы; APP-01 — ближайший блокер |
| Реальная подготовленная схема и данные информационной базы | Не приняты; APP-02/APP-05 |
| Открытие существующей информационной базы реальным клиентом 1С | Не принято; успешного сквозного прогона нет |
| Выполнение и проверка результата теста Гилёва на Firebird | Не принято; успешного сквозного прогона нет |

Нынешнее состояние — окончание основного фундамента и переход к прикладным
каталогам/типам. Последние BLOB-этапы устранили реальный пробел обмена данными,
но не заменили проверки, которые 1С делает до чтения конфигурации.

## Ближайший путь

1. **Каталоги для открытия базы (APP-01).** [APP-10: namespace registry](NAMESPACE_REGISTRY_TASK.md)
   принят: SQL-only основа устойчивых native IDs.
   [APP-11: публичный namespace view](NAMESPACE_CATALOG_TASK.md) реализован и
   оставлен на review, с native именами и BIGINT/VARCHAR metadata. Далее согласовать
   PG/native имена, regnamespace/oid/name, pg_class, search-path visibility и temp namespace,
   чтобы выполнить selected04 с реальными объектами. Для selected05 отдельно
   определить честный current_database/collation contract; имя native collation
   нельзя просто выдать за PostgreSQL LC_COLLATE.
2. **Типы и настоящая схема (APP-02/05).** SQL bytea и представление binary IDs
   с требуемыми сравнениями/индексами, mchar/mvarchar с проверкой регистра,
   пробелов и Unicode, BINROWVER. Выбрать минимальные native механизмы; только
   после этого готовить схему и переносить реальные служебные данные/конфигурацию.
   Каталоги и типы частично зависят друг от друга, это не два больших монолитных патча.
3. **Первое реальное открытие 1С (APP-06, промежуточная точка).** Подключить
   реальный клиент к подготовленной базе, проверить фактическую библиотеку,
   startup/options/OIDs/formats и первый неработающий запрос. Не менять строку
   версии сервера и не возвращать фиктивные результаты ради прохождения проверки.
4. **Нагрузка Гилёва (APP-03/04/05).** Реальные shared/exclusive advisory locks
   между соединениями, нужные временные объекты/serial/ANALYZE/fasttrun, DML и
   version predicates. Проверять семантику и эффекты, включая rollback и конкуренцию,
   а не только успешное завершение запросов. Затем реальный тест Гилёва и сравнение
   результата; текущая запись не является готовым последовательным replay.
5. **Окончательная приёмка (APP-06/VAL-05).** Зафиксировать версии/настройки,
   native coexistence, права, очистку, concurrency и согласованные ограничения.
   Удалённый TCP/TLS/cancellation и другие открытые wire/platform пункты также
   остаются в backlog; локальный функциональный успех не закрывает их автоматически.

Условие перехода к следующему этапу — конкретный принятый результат. После APP-10/11
нельзя объявлять APP-01 закрытым: сам selected04 ещё требует остальных частей.
Это порядок приоритетов, не гарантия, что locks/temporary DDL понадобятся только
после открытия базы: selected10/11/12 появляются уже в начале записи. Такие части
могут потребоваться для первого открытия; порядок уточняется фактическим отказом.
Большие input BLOB (APP-09) сохраняются, но не вытесняют ближайшую работу над
каталогами, если очередной реальный сценарий не потребует их раньше.

## Что ещё не доказано данными записи

Исходная запись не содержит полных Startup/Bind/result formats и всех ответов
сервера. DETAIL — текстовое представление параметров, не исходные Bind bytes.
Успех через libpq 14.24 не доказывает, что 1С загрузила ту же библиотеку; в исходном
исследовании поставляемая с 1С библиотека на диске сообщала 14.2, путь в процессе
не проверялся. Создание новой базы средствами 1С и загрузка .dt — отдельные
сценарии, не принятые этой записью открытия существующей базы/Гилёва.
