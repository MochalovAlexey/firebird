## 3. Результат этого этапа и границы

Реализовать настоящий переключатель:

    SET standard_conforming_strings = off;
    SET standard_conforming_strings TO on;

Начальное значение — on. Поддержать on/off без учёта регистра, как идентификаторы
и строковые значения, используя существующую форму SET. Неподдержанные значения
должны давать явную ошибку, согласованную с действующим профилем настроек;
не трактовать произвольную строку как bool.

При on обычные строковые литералы сохраняют существующее поведение.
При off engine parser действительно обрабатывает backslash escapes обычных
строк. Например, текст SELECT '\n' означает два символа при on и один перевод
строки при off.

Обязателен законченный путь: SET → состояние движка → parser/cache →
Simple/Extended Query → фактические значения → откат и уведомление клиента.
Не подменять его отдельным E-literal decoder или успешным ответом SET
без изменения разбора строк.

Отдельными целями не являются E'...', dollar quoting, SET LOCAL, SET SESSION,
DEFAULT, SHOW, RESET parameter, другие настройки стартового пакета,
BEGIN/$n/::/LIMIT, каталоги, bytea, TLS или cancellation.
ALTER SESSION RESET уже существует и должен корректно сбрасывать новую настройку.
Не добавлять сопутствующий синтаксис автоматически ради полноты PostgreSQL.
Оставшиеся неподдержанные формы явно перечислить в документации.

Native синтаксис, существующие codecs и правила других session setters сохраняются.
Не добавлять production timeouts и не исправлять ранее отложенные native дефекты:
shutdown во время ON CONNECT и READ CONSISTENCY + AUTO COMMIT.

## 4. Согласованная архитектура

### 4.0. Причина изменения решения

Исполнитель уже исследовал поведение на отдельном эталоне 18.6 через настоящий
libpq. Настройка восстанавливается сразу после ошибки, ещё в состоянии E:

| Последовательность | Значение после ошибки |
| --- | --- |
| BEGIN → SET off → SELECT 1/0 | on, E, до явного ROLLBACK |
| BEGIN → SET off → syntax error | on, E |
| BEGIN → SET off → SAVEPOINT a → SET on → SAVEPOINT b → SET off → ошибка | on, то есть значение на входе в b |
| Затем успешный ROLLBACK TO a | off, T |

Полные свидетельства предыдущего прогона:
/tmp/pgwire-1c-reference-iss_20tu/summary.json и
/tmp/pgwire_strings_abort_probe.py. Проверено 14 запросов, сервер завершился
с кодом 0; рабочая база не менялась. Это внешние временные артефакты:
их наличие проверить, обязательные ожидания перечислены в этой инструкции.
BEGIN здесь относится к эталону; Firebird тестировать существующим
SET TRANSACTION, не добавляя BEGIN в данный этап.

Ошибка может возникнуть только в плагине, например duplicate prepared name.
Движок её не видит. getInfo читает состояние, prepare override управляет
разбором, а полный rollback уничтожил бы нужный recovery через savepoints.
Поэтому историю и решение о восстановлении теперь хранит плагин.
Не останавливайся повторно на уже разобранном препятствии; реализуй этот вариант.

### 4.1. Одно текущее значение в движке

Attachment владеет текущим значением настройки. Расширить существующий
SetPgSessionNode: изменение происходит при Execute, не при prepare/Parse/Bind.
Использовать обычную инфраструктуру parser и session statements.
PG-only keyword gate должен сохранять native identifiers и диагностику.

В движке это обычная session-настройка. Для неё не добавляется PostgreSQL-undo
в native transaction/savepoint lifecycle. Успешный ALTER SESSION RESET возвращает
режим on через существующий путь сброса attachment.

Явная граница контракта: прямой OO API с PG dialect 4 поддерживает SET, parser,
cache и prepare flags, но native rollback автоматически эту session-настройку
не восстанавливает. PostgreSQL-семантика её отката обеспечивается именно PgWire.
Зафиксируй и проверь это различие, не заявляя полный PG session contract для OO API.

### 4.1.1. История на подключение в PgWire

Разместить минимальное состояние в существующем QueryExecutor/его session objects:

- snapshot настройки на входе в логическую implicit/explicit transaction;
- имя и snapshot для действующих пользовательских savepoints;
- последнее отправленное ParameterStatus, если нужно для исключения повторов.

Это история одной настройки, не копия native undo журнала данных и не общий GUC
framework. После успешного пользовательского SET читать фактический bool через
getInfo; не разбирать его значение в плагине.

История должна существовать до первого изменения настройки в логическом блоке.
Отсутствие ITransaction handle не означает отсутствие этого блока:
session SET может исполниться до ленивого начала native transaction.
Не создавай отдельную транзакцию для SET, prepare или служебного восстановления.
Сохрани прежнее владение единственным application handle.

Границы истории:

- Simple Query: implicit сегмент до полного COMMIT/ROLLBACK либо завершения Query.
  Следующий сегмент начинает новую историю. Например, SET off; SELECT 1/0
  в одном Query возвращает прежнюю настройку, даже если handle ещё не появился.
- Extended Query: implicit цикл до Sync, охватывающий несколько сообщений,
  включая Flush и несколько Execute. История не сбрасывается после каждого
  сообщения или SET. Parse/Bind не исполняют SET, но их ошибки могут отменить
  уже исполненный SET текущего блока.
- Explicit transaction: до реального полного завершения; ошибка сохраняет native
  transaction в E. COMMIT из E уже превращается в ROLLBACK — история должна
  следовать фактическому действию executor, а не тексту команды.

При первой ошибке уровня немедленно восстановить snapshot последнего активного
пользовательского savepoint либо начала блока, если savepoints нет. Историю,
нужную для последующего ROLLBACK TO, сохранить. Повторная ошибка в E не должна
откатывать ещё один внешний уровень или повреждать историю. Обработчики Simple
и Extended должны использовать одну согласованную логику восстановления.

Изменять структуру истории savepoints после успешного native execute.
Failed control не считается выполненным; его ошибка проходит обычный abort path.
При успешном ROLLBACK TO восстановить snapshot целевой точки, удалить более
поздние и сохранить возможность повторного возврата к целевой точке.
COMMIT сохраняет текущее значение; полный ROLLBACK восстанавливает snapshot блока.
При retaining/reset согласовать историю с фактическими границами и состоянием
уже поддержанных native controls, включая замену underlying transaction
при том же interface pointer. Успешный reset очищает прежнюю историю.

Нужно узко расширить SqlInfo: извлекать имя SAVEPOINT/ROLLBACK TO/RELEASE SAVEPOINT
и различать ONLY после проверки грамматики движком. Сопоставление имён должно
следовать Firebird, включая quoted identifiers, doubled quotes, регистр, UTF8
и обработку концевых пробелов. Используй существующие общие helpers, например
пригодные части FrontendLexer/MetaString; Jrd::MetaName зависит от контекста БД
и не должен переноситься в плагин.

Сохранить уже поддержанную native-семантику:

- повторный SAVEPOINT name заменяет прежнюю одноимённую точку;
- RELEASE SAVEPOINT name удаляет целевую и более поздние точки;
- RELEASE SAVEPOINT name ONLY удаляет только указанную точку.

Не вводи поверх Firebird другую семантику повторных имён. Хранить требуется
только пользовательские точки, видимые в поддержанном SQL control path,
без отслеживания внутренних statement/PSQL savepoints движка.
Проверь resource/error paths: если native команда уже выполнилась, а обновить
историю корректно не удалось, нельзя продолжать с рассогласованным состоянием.

Гарантия нового PG-отката настройки относится прежде всего к обычным блокам
PgWire без native AUTO COMMIT. Native AUTO COMMIT может делать commit retaining
внутри движка, очищая savepoints без отдельной клиентской команды; вложенный
RESET тоже требует проверки. Не считай interface pointer или смену transaction
ID достаточным описанием такого события. Существующий native AUTO COMMIT
не удаляй и не меняй; для сочетаний с новой настройкой явно зафиксируй
подтверждённое поведение либо ограничение, без нового общего lifecycle API.
Отдельным целевым тестом проверь, что EXECUTE BLOCK / EXECUTE STATEMENT с
внутренними savepoints не повреждает историю внешних пользовательских точек.
PG SET внутри PSQL пока остаётся запрещён существующим guard.

### 4.1.2. Восстановление через существующий SQL API

Выбранный snapshot применять одной из двух фиксированных служебных команд:

    SET standard_conforming_strings = on
    SET standard_conforming_strings = off

Исполнять через существующие prepare/execute API того же attachment,
напрямую, минуя пользовательский Query dispatcher и его запрет 25P02 в E.
Никаких новых методов, callbacks или API abort-current-level не добавлять.
Служебный SQL составляется только из двух констант, не из входного текста.
Это не переписывание пользовательского запроса.

Служебное исполнение не должно запускать пользовательский SQL, рекурсивно менять
журнал, создавать отдельную транзакцию, менять I/T/E или отправлять клиенту
CommandComplete/ReadyForQuery за внутренний SET. Оно меняет только настройку
attachment, сохраняя native transaction и возможность последующего recovery.
Используй обычный session-management execute без собственного transaction handle.

После успешного восстановления получить/подтвердить фактическое значение
и согласовать ParameterStatus. При неудаче восстановления завершить соединение
с FATAL и обычной очисткой ресурсов; не выдавать желаемое значение за действительное.
Не заменять исходную ошибку произвольным успешным ответом.
Fatal/непригодное подключение не пытаться сделать пригодным служебным SET.

Если решишь переиспользовать подготовленные служебные statements, учти их
ownership, освобождение и invalidation при reset. Новый statement cache или
универсальный слой внутренних запросов для двух констант не нужен.

### 4.2. Engine parser и исходный SQL

Декодирование выполнять в существующем parser/lexer Firebird, только для PG4
и соответствующего эффективного режима. Использовать существующие IntlString,
представление литералов, charset/Unicode helpers и проверки длины.
Новые узлы выражений и отдельная библиотека не требуются. Плагин передаёт
исходный SQL без переписывания; штатное внутреннее преобразование сохраняемого
SQL в движке допустимо для сохранения смысла литералов.

Сверить с PostgreSQL обработку кавычек, обратной косой черты, управляющих,
octal/hex и Unicode escapes, неизвестных escapes, недопустимых кодовых точек,
нулевого байта, некорректного UTF8 и ограничения длины. Не подменять неизвестную
или ошибочную последовательность произвольным символом. Неполный контракт
нужно явно обозначить; короткий набор положительных примеров не доказывает
совместимость всего decoder.

Проверяемый wire-профиль — UTF8. PG4 доступен и через OO API, поэтому нельзя
молча считать любой attachment UTF8. Используй штатную конверсию либо явно
и корректно откажи неподдержанному charset для новой возможности.

Сохраняй исходные offsets для ошибок и выделения команд. Проверь StrMark,
transformString, сохранение исходников DDL/PSQL и последующие внутренние prepare.
Не ставь introduced-флаг произвольно: существующая логика связана с _charset.
Используй штатные механизмы сохранения смысла литерала; если какой-либо
вложенный/сохранённый случай пока нельзя поддержать корректно, откажи явно
и задокументируй ограничение, не допуская тихой смены значения.

### 4.3. Узкое расширение существующего публичного контракта

Согласованы:

1. Один новый info item существующего IAttachment::getInfo для текущего режима.
   Сигнатура, vtable и версия интерфейса не меняются. Использовать обычный
   формат info items и штатные helpers кодирования/чтения; аналог — frb_info_att_charset.
   Это расширение набора запрашиваемых данных, а не новый метод.
2. Два флага существующего prepare: явно использовать on или явно использовать off.
   Сигнатура prepare не меняется. Без обоих флагов режим берётся из attachment.
   Override действует только на данную подготовку и не меняет attachment.
   Взаимоисключающие флаги проверяются; вне PG4 они не должны включать PG-семантику.

Выбрать свободные номера по актуальным исходникам; не расширять набор методов,
не добавлять новые statement command/origin metadata.
Для восстановления текущего значения уже существует API исполнения SQL:
дополнительный mutator/read-write getInfo не требуется и не согласован.
Проверить прохождение flags через существующие слои, ширину полей и masks.
Если потребуются generated bindings, обновить их штатным генератором.
Не принимать отсутствие нового info item у несовместимой сборки за значение on.

### 4.4. Эффективный режим, cache и Extended Query

Эффективный режим определить один раз для конкретного prepare: override,
если передан, иначе текущее значение attachment. **Один и тот же режим**
использовать в parser и ключе DSQL cache, включая помещение в cache.
Native dialects не должны зависеть от PG-настройки.

Одинаковый текст SELECT '\n' при on и off имеет разные значения литерала.
Поэтому в существующий ключ cache добавить необходимый признак режима.
Простая очистка cache при SET не решает проблему повторной подготовки старого
prepared statement.

Сейчас Extended Parse готовит SQL, а каждый Bind снова готовит source.sql
для отдельного portal. Причина — независимые cursors: один Firebird statement
допускает один открытый cursor. Сохрани эту модель и её ownership.

- При Parse прочитать режим, сохранить его в существующем Prepared и передать
  этот же режим первоначальному prepare.
- При каждом Bind использовать сохранённый режим для повторного prepare,
  независимо от текущего значения attachment.
- Это историческое условие разбора подготовленного SQL, а не второй источник
  текущей настройки сессии. Bind-параметры остаются значениями и не проходят
  через SQL escape decoder.

Обязательный пример: именованный Parse при on → отдельный SET off →
Bind/Execute прежнего запроса. Прежний запрос должен сохранить два символа.
Используй также CAST('\n' AS VARCHAR(8)), чтобы изменение длины metadata
не скрывало ошибку интерпретации результата.

### 4.5. Simple Query и согласованность лексеров

В начале каждого сообщения Query прочитать и сохранить один режим.
Этот snapshot передать FrontendLexer и всем prepare данного сообщения,
включая продолжения кандидата EXECUTE BLOCK по AUTOTERM.
SqlInfo должен согласованно пропускать строки при своей ограниченной
классификации. Только parser движка вычисляет значение литерала.

Например, при off:

    SELECT 'a\';b'; SELECT 2;

содержит две команды. Значение первой строки — a';b; первая точка с запятой
находится внутри литерала. Lexer не должен принять экранированную кавычку
за конец строки. Сохрани native/isql режим FrontendLexer по умолчанию.

Если сообщение началось при on:

    SET standard_conforming_strings = off;
    SELECT '\n';

SELECT в этом же сообщении всё ещё использует on, хотя SET уже изменил attachment.
Следующее сообщение Query использует off. В PostgreSQL это следствие разбора
всего сообщения до исполнения. У нас достаточно snapshot режима:
предварительный parser всего пакета не добавляется, исполнение остаётся
последовательным с остановкой на первой ошибке.

### 4.6. ParameterStatus

Сейчас startup всегда сообщает standard_conforming_strings=on.
После появления изменяемого режима источник фактического значения — getInfo.
Передавать актуальный ParameterStatus при startup и изменениях/восстановлении
настройки, включая error cleanup, rollback/savepoints и reset.
Согласовать момент уведомления с Simple/Extended message flow.

Плагин может хранить последнее отправленное значение для исключения повторных
сообщений. Нельзя считать его самостоятельной настройкой и вычислять новый режим
по тексту SET: исполнение может завершиться ошибкой или впоследствии откатиться.

## 6. Реализация и проверки

Сначала кратко изложи фактические точки изменения после чтения кода.
Затем реализуй описанный этап; не останавливайся только на плане.
Удобный порядок: decoder/prepare context/cache → обычный session SET/getInfo →
plugin history и служебное восстановление → wire snapshots/ParameterStatus →
целевая приёмка и документация.
Промежуточные части не коммить и не объявляй законченным этапом.

Расширяй имеющиеся src/plugins/wire/pg/tests, src/isql/tests
и pg_wire_protocol/tools. Новый test framework не нужен.
Положительные сетевые проверки выполняй через настоящий libpq; raw wire
нужен для точного порядка Parse/Bind/Execute и сообщений ParameterStatus.
Прямой OO API полезен для проверки prepare flags, cache и native isolation.

Минимальная содержательная приёмка:

| Область | Что доказать |
| --- | --- |
| Реальные строки | on/off, кавычки и backslashes, управляющие/числовые/Unicode escapes, ошибки и граничные длины; сравнивать байты/значения, SQLSTATE и metadata |
| SET | Изменение только при Execute; неподдержанное значение не применяется, но ошибка может откатить прежние SET текущего уровня; prepared SET можно исполнять повторно |
| Контракт | getInfo возвращает фактический режим; prepare override не меняет attachment; default и ошибочные flags обработаны; прямой OO API не обещает PG-откат настройки |
| Cache | Один SQL on → off → on, без чужого плана; override отличается от attachment; native1/2/3 и PG4 не смешиваются |
| Extended | Named Parse → SET → Bind сохраняет исходный литерал, в обе стороны; несколько portals сохраняют независимые cursors; Bind-значения не декодируются как SQL |
| Simple Query | Экранированная кавычка перед semicolon; один snapshot всего Query; новое сообщение видит новое значение; один ReadyForQuery; остановка на первой ошибке |
| Транзакции | Implicit failure, explicit commit/rollback, несколько изменений, вложенные savepoints/release/repeated rollback-to, I/T/E recovery и поддержанные retaining controls |
| Ошибки до Execute | Syntax/prepare error, duplicate named prepared statement и ошибка Bind после уже выполненного SET немедленно восстанавливают нужный уровень; повторные ошибки в E не откатывают внешний |
| Логические границы | SET до появления native handle; несколько Execute/Flush до Sync; переход к новому implicit сегменту после COMMIT; COMMIT в E реально откатывает историю |
| Имена savepoints | Quoted/doubled quotes/UTF8/концевые пробелы, повторные имена, RELEASE с ONLY и без, failed controls; соответствие настоящим native savepoints |
| Служебное восстановление | Нет лишних wire results/transaction handles, изменения I/T/E или рекурсивных записей истории; при отказе восстановления нет ложного ParameterStatus и продолжения с рассогласованием |
| Изоляция/reset | Два подключения с разными режимами; ALTER SESSION RESET; отсутствие утечек режима в другие attachments и native SQL |
| Wire status | Фактический ParameterStatus и libpq PQparameterStatus после изменения, ошибки/отката и reset; соответствие текущему состоянию движка |
| Parser regression | Native dialects 1/2/3, Q-strings, comments, EXECUTE BLOCK и AUTOTERM; новый keyword как native identifier; корректные границы и диагностики |
| Сохранённый SQL | DDL/PSQL или явный отказ неподдержанному случаю; отсутствие смены смысла литерала после внутренней переподготовки/переподключения |

Для сценариев немедленного восстановления используй ожидаемые значения из §4.0.
Отдельно покажи, что PG-история не зависит от native root undo savepoint:
достаточна соразмерная проверка NO AUTO UNDO, новый stress framework не нужен.
Не смешивай обычные implicit transactions PgWire с native TPB AUTO COMMIT:
поддержку второго в сочетании с новой настройкой доказывать отдельно либо
чётко исключить из подтверждённого профиля, сохранив прежнюю native возможность.

Не задавай ошибкам неверный isc_command_end_err2: script reader считает его
признаком необходимости продолжить кандидат. В предыдущем этапе grammar-only
YYERROR gate уже ломал native AUTOTERM; исправление сделано через PG-only
token gate. Повторно проверь эту границу при новом keyword.

После целевых проверок выполни затронутую регрессию: существующие fixed settings,
scripts, Simple/Extended и transaction/native проверки. Масштабируй набор
по фактическим изменениям; не запускай бесконечно все suites после успешной
приёмки без новых причин.
